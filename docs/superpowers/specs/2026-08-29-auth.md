# Real authentication for KIRA+

Status: approved by Aliff (2026-08-29), ready for implementation planning.

## Problem

KIRA+'s MVP deliberately has no authentication — every profile is either a synthetic demo persona
or a hand-typed session-scoped entry, matching `docs/MASTER-PACKAGE.md`'s stated roadmap trigger
("first real user data") and its Privacy Architecture principle ("we don't need to know who you are
to understand your financial health"). Aliff has decided to build real auth now, ahead of that
trigger, so that saved profiles persist per-user instead of being anonymous/session-only.

This is deliberately scoped to **not require a frozen-contract change**. `docs/API-CONTRACT.md`'s
`Profile` type is scoring input — seven numeric fields, no identity — and stays exactly as frozen.
Who *owns* a saved profile row is a storage/access-control concern, not a scoring-input one, so it
lives entirely in `backend/database/schema.sql` and the FastAPI transport layer (both Aliff's
ownership per `docs/HANDOFF.md`), never in the `Profile` JSON shape itself. No `contract_version`
bump, no `data/mock-data.json` change, no sign-off needed from Arjun under the contract's own §8
governance rule — because nothing §2-§5 or §9 defines actually changes.

## Non-goals

- No password reset / email verification in v1 (register + login only) — avoids pulling in an
  email-sending dependency nobody's needed yet.
- No refresh-token pair — a single ~30-day JWT, no rotation, no revocation list.
- No login wall on any existing page. Demo personas and filling out the profile form stay completely
  frictionless and unauthenticated; only the *save* action gates on being logged in.
- No changes to `docs/API-CONTRACT.md`, `data/mock-data.json`, or any `backend/utils/`,
  `backend/models/`, `scoring_service.py`, `llm_service.py` file — Arjun's domain is untouched.
- No changes to `POST /assess`, `/simulate`, `/simulate/grid`, `/explain` — they compute statelessly
  on a `Profile` object in the request body; there's no owned/stored data there to protect, so
  gating them on auth would be friction with no security benefit.

## A. Database

Two changes to `backend/database/schema.sql` (Aliff's file):

```sql
CREATE TABLE users (
    user_id       INTEGER PRIMARY KEY AUTOINCREMENT,
    email         TEXT NOT NULL UNIQUE,
    password_hash TEXT,              -- NULL for Google-only accounts
    google_sub    TEXT UNIQUE,       -- Google's stable user id; NULL for password-only accounts
    created_at    TEXT NOT NULL DEFAULT (datetime('now'))
);
```

```sql
ALTER TABLE profiles ADD COLUMN user_id INTEGER REFERENCES users(user_id) ON DELETE CASCADE;
```

`user_id` is nullable — existing demo-profile rows (`is_demo=1`) stay ownerless and public. Only
profiles saved by a logged-in user get a `user_id`. No migration/backfill concern: no real data
exists yet, so `init_db.py`'s existing drop-and-recreate approach just picks up the new schema.

## B. Backend

New files, following the existing `app/` (transport) → `services/` (orchestration) → `utils/`
(pure functions) layering exactly:

- `backend/utils/auth.py` — pure functions, no `fastapi` import: password hashing/verification
  (bcrypt), JWT encode/decode (PyJWT, HS256).
- `backend/services/auth_service.py` — orchestrates `utils/auth.py` + the `users` table. Raises
  plain Python exceptions on failure (new `EmailAlreadyRegistered`, `InvalidCredentials` in
  `backend/errors.py`, alongside the existing `ValidationError`) — never an `HTTPException`,
  matching the existing rule that services never import `fastapi`.
- `backend/app/routers/auth.py` — transport only. Catches `auth_service`'s exceptions and maps them
  to HTTP status codes (mirrors how `main.py` already handles `ValidationError` → 422).

New dependencies in `backend/requirements.txt`: `PyJWT`, `bcrypt`, `google-auth` (for verifying
Google ID tokens against Google's public keys — no client secret needed for this flow).

New env vars (`backend/.env.example`): `JWT_SECRET`, `GOOGLE_CLIENT_ID`.

### Endpoints

| Route | Request | Response | Auth required |
|---|---|---|---|
| `POST /auth/register` | `{email, password}` | `{token}` | No |
| `POST /auth/login` | `{email, password}` | `{token}` | No |
| `POST /auth/google` | `{id_token}` | `{token}` | No |

`POST /auth/google` verifies the raw Google ID token's signature via Google's public keys, extracts
`email` and Google's stable `sub`, and upserts a user: match existing account by `google_sub` first,
then by `email` (so someone who registered with a password can also sign in with Google on the same
account), otherwise create a new user with `password_hash = NULL`.

**Password rule:** minimum 8 characters, no other complexity requirement — checked in
`auth_service.register`, returns the existing `ValidationError` shape (`{field: "password", message:
"Password must be at least 8 characters."}`) on failure, consistent with how `profile_service`
already validates input before touching the database.

JWT payload: `{sub: user_id, email, iat, exp}`, HS256, ~30-day expiry. A reusable FastAPI dependency,
`get_current_user`, extracts and verifies the `Authorization: Bearer <token>` header, raising 401 if
missing, malformed, or expired.

### Route protection changes

Only the storage routes change:

- `POST /profiles` — now requires `get_current_user`; stamps the new row with the caller's `user_id`.
- `GET /profiles` — filters to the caller's own profiles only.
- `GET /profiles/{profile_id}` — 404 (not 403) if the profile exists but belongs to someone else —
  don't leak that a given `profile_id` exists to someone who doesn't own it.
- `GET /profiles/demo/{name}` — unchanged, stays fully public.

## C. Frontend

**New pages**, `/login` and `/register`, under the `(marketing)` route group — `MarketingNav` frames
them, no new shell needed for two forms. Each: email + password fields, submit, plus a "Sign in with
Google" button using Google's own client-side library (`accounts.google.com/gsi/client`, loaded via
a plain `<script>` tag — works fine in the static export, no server involved). That flow hands the
browser an ID token directly; the frontend POSTs it to `/auth/google`.

New env var (frontend build-time): `NEXT_PUBLIC_GOOGLE_CLIENT_ID` — same Google client ID the backend
verifies against (client IDs aren't secret; only a client *secret* would be, and this flow needs none).

**Token storage** — new `lib/authStorage.ts`, mirroring the existing `lib/profileStorage.ts` pattern
exactly: `getToken()`, `setToken(token)`, `clearToken()`, localStorage-backed.

**`lib/api.ts`** — the shared `request()` helper attaches `Authorization: Bearer <token>`
automatically whenever a token exists. Every existing call site (`saveProfile`, `loadProfile`, etc.)
needs zero changes for this. New functions: `register(email, password)`, `login(email, password)`,
`loginWithGoogle(idToken)` — each resolves `{token}`; the page that calls them stores it via
`authStorage.setToken`.

**What gates on login:** nothing at the page level. All four app-shell pages keep working exactly as
today — demo personas, filling in the form, all frictionless. The only new gate is `saveProfile()`
itself: on a 401, the Profile page catches it and redirects to `/login`. Re-filling the form after
logging in is an acceptable v1 rough edge, not solved here.

**`MarketingNav`'s placeholder button, closed:** it currently always links to `/dashboard`. Now it
checks `authStorage.getToken()` — present → "Dashboard" (unchanged), absent → "Log in" (→ `/login`).
This is exactly the slot `docs/superpowers/specs/2026-08-29-mobile-shell-redesign-design.md` flagged
as standing in for login.

**Logging out:** a "Log out" action on the `/profile` page (the existing account-context screen) —
clears the token via `authStorage.clearToken()` and redirects home. No change to `AppNav` itself
(already tight at `justify-between` on desktop, four fixed tabs on mobile).

## D. Testing

**Backend** (new tests, following the existing stub-first pattern): password hash round-trips; JWT
encode/decode and expiry; `register` rejects a duplicate email; `register` rejects a password under
8 characters with the `ValidationError` shape; `login` rejects a wrong password;
Google-token verification (mocked — no real network call to Google in tests); `POST /profiles`
returns 401 with no token; a user cannot `GET` another user's saved profile (404, not 403); demo
endpoints stay reachable with zero auth headers.

**Frontend** (new tests): `authStorage.ts` unit tests (mirroring `profileStorage.test.ts`); a test
that `lib/api.ts`'s `request()` attaches the header when a token exists and omits it when it doesn't;
`MarketingNav` tests for both the logged-in and logged-out button states; a `saveProfile` 401 →
redirect-to-`/login` test on the Profile page.

## E. Rollout

No real data exists yet — every current row is synthetic/demo. `ALTER TABLE profiles ADD COLUMN
user_id` runs clean via `init_db.py`'s existing drop-and-recreate approach; no backfill needed.

## Decisions log

Resolved by Aliff (2026-08-29), via interactive brainstorm (no visual companion needed — every
question here was conceptual/text, not visual):

- **Frozen contract:** left untouched. `user_id` lives in the database and transport layer only,
  never in the `Profile` JSON shape — no `contract_version` bump, no Arjun sign-off needed, since
  nothing `docs/API-CONTRACT.md` §2-§5/§9 defines actually changes.
- **Token transport:** `Authorization: Bearer` header + localStorage, not a cross-domain cookie —
  avoids `SameSite`/`credentials`-mode complexity between the two different origins
  (`kiraplus.aliffaizuddin.uk` / `api-kiraplus.aliffaizuddin.uk`), fits the existing fetch-based
  `lib/api.ts` pattern directly.
- **Google OAuth shape:** client-side ID token (Google Identity Services), not the server-side
  authorization-code flow — no client secret needed, no redirect-relay-back-to-a-static-frontend
  problem to solve.
- **Password auth scope:** register + login only, no reset/verification, for v1.
- **Session length:** single JWT, ~30 days, no refresh-token pair.
- **What requires login:** only saving/loading a *real* profile. Demo personas and the profile form
  itself stay completely public and frictionless.
- **Logout placement:** on `/profile`, not in `AppNav` itself.
